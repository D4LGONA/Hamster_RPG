# 부하 테스트 1차 (2026-09-25)

> 대상 커밋: `7304d80` (패킷 재조립 + 세션 수명 개편 직후)  
> 목적: 성능 튜닝이 아니라 **어제 고친 접속/끊김 코드가 부하에서 안 터지는지** 확인.

---

## 1. 실행 방법

```bash
Server/x64/Debug/Server.exe --random-spawn 25 --profile
python Tools/loadtest.py --area 25 --no-viz --duration 150 --max-bots 800 --ping-rise 30
```

- 봇을 계속 밀어 넣다가 핑이 기준선보다 30ms 오르면 한계로 보고, 그 위에서 진동시킨다.
- `--ping-rise` 기본값(10)으로 먼저 돌렸더니 8명에서 가짜 한계가 잡혔다.
  틱 대기(0~67ms)가 핑에 섞여서 노이즈가 10ms를 넘는다. 30으로 올려서 다시 쟀다.
- **Debug 빌드**이고, 봇이 ±25 안에 몰려 있어(한 명당 40명 정도가 시야에 들어옴) 일부러 빡센 조건이다.

## 2. 결과: 세션 누수·크래시 (이번 테스트의 본래 목적)

| 로그 | 횟수 |
|---|---|
| `[ACCEPT]` | 239 |
| `[DISCONNECT]` | 239 |
| `[SESSION REMOVED]` | 239 |

- 239:239:239으로 **세션이 하나도 map에 남지 않았다.** 크래시 없음.
- 테스트 후 서버 메모리 14MB, `players=0`으로 정상 복귀.
- `[SEND ERROR] 10053/10054`가 982번 발생했다. 봇이 먼저 끊어서 나는 정상 에러이고,
  **Send 실패로 연결을 끊는 경로**(세션 수명 개편의 핵심 경로)가 982번 밟혔다는 뜻이다.
  그 상태에서 누수가 0이라는 점이 이번 테스트의 소득이다. → [SessionLifetime.md](SessionLifetime.md)
- 어제 남겨 둔 의문 두 가지도 같이 확인됐다.
  - `extOver == nullptr` 분기에서 세션이 남지 않는다(소켓 닫힘 → Recv 실패 완료 → `RemoveSession`).
  - `[DISCONNECT]` 로그는 정상적으로 찍힌다(로그인한 플레이어 기준).

## 3. 성능 기준선

| 항목 | 값 |
|---|---|
| 안정 동접 | **111명** (한계 134명에서 핑 81.5ms, 기준선 48.2 + 30) |
| 틱 평균 / 최대 | **53~66ms / 104ms** (목표 66.7ms = 15Hz) |
| CPU | 게임 틱 스레드 1개가 **1.0~1.3코어**. 워커는 거의 논다 |
| 접속 실패 | 0 |
| 누적 | 수신 8,074,064 패킷 / 124.6 MB |

### 틱 한 번의 내역 (평균 66ms 기준)

```text
5.send        40.5ms   61%  ← 병목
3.playerDiff  17.5ms   26%  시야 비교
1.integrate    7.6ms   11%  이동 적용
4.monsterDiff  0.8ms
2.monsterAI    0.2ms
lock           0.01ms        락 경합은 사실상 없음
```

- 병목은 **패킷 전송**이다. 틱 스레드가 패킷을 직접 다 보내고 있다.
- `lock`이 0.01ms라 coarse `playersLock`은 아직 문제가 아니다. 틱 스레드의 일 자체가 많다.

## 4. 해석과 다음

- 기능이 더 붙으면 병목이 바뀌므로 **지금 최적화하지 않는다.** 이 문서는 나중 비교용 기준선이다.
- 최적화 시점이 오면 후보는 이 순서다.
  1. 전송을 틱 스레드에서 워커로 넘기기 / 패킷 묶어 보내기 (`5.send`)
  2. 시야 비교 비용 줄이기 (`3.playerDiff`)
  3. 그 다음에야 `playersLock` 쪼개기 (지금은 경합이 없어서 효과가 없다)
- 다시 잴 때는 **Release 빌드**로도 한 번 재서 Debug와의 차이를 남겨 둘 것.
